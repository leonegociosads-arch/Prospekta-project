Prospekta: encontrar os melhores leads gastando quase nada

Uma análise completa antes da primeira linha de código: como a ferramenta é organizada, como usar a Google Places API sem sair da cota gratuita, o que dá pra fazer só com código, onde a IA realmente compensa, e em que ordem construir. Escrito para quem está começando.

Next.js + TypeScript Supabase Free Google Places API (cota grátis) Cache + orçamento por pesquisa Worker local IA só no topo do funil
O que mudou da v0 para a v1 O teste no OpenStreetMap deu 8 estabelecimentos no total em Iguape + Ilha Comprida — cobertura insuficiente. O OSM sai como fonte principal de descoberta. Entra a Google Places API, com uma camada inteira de controle de custo desenhada em volta dela (cache, deduplicação por Place ID, orçamento de chamadas por pesquisa, teto mensal). As fontes agora são plugáveis: trocar ou somar outra fonte no futuro não mexe no resto do sistema.

01 Arquitetura geral

A visão de cima: quais peças existem e como conversam entre si.

O Prospekta tem quatro peças, e só. Quanto menos peças, menos coisa pra aprender, instalar e depurar.

1. O painel (aplicação web) — Next.js + TypeScript

É a tela que você abre no navegador. Nela você cria uma pesquisa (cidade, raio, nicho), acompanha o progresso, vê o ranking de leads e abre o diagnóstico de cada um. Roda no seu computador durante o desenvolvimento (localhost:3000) e, se um dia quiser, sobe de graça na Vercel.

2. O banco de dados — Supabase (PostgreSQL) Free

É onde tudo fica guardado: pesquisas, leads, análises de site, sinais de anúncio, scores. O Supabase é um Postgres hospedado de graça, com um painel visual pra ver as tabelas e uma biblioteca pronta pra o Next.js conversar com ele.

3. O trabalhador (worker) — um script Node que roda na sua máquina

Encontrar empresas e analisar dezenas de sites é lento (segundos por site). Isso não pode travar o painel. Então existe um segundo programa — o worker — que fica olhando o banco, pega tarefas pendentes (“analisar o site do lead X”), executa e grava o resultado. Você liga ele com um comando (npm run worker) quando quer processar uma pesquisa.

4. Serviços externos — chamados pelo worker, sempre passando pelo “porteiro”

Google Places API (lista de empresas + telefone + site + avaliações), PageSpeed Insights (desempenho do site), Meta Ad Library (indícios de anúncio) e, só no fim do funil, uma API de IA barata. Nenhuma chamada à Google sai direto: ela passa primeiro por dois módulos internos —

  • Cache — “já temos esse dado no banco e ainda está válido? Então não chama.”
  • Orçamento (o porteiro) — “essa pesquisa já gastou o limite de chamadas? O teto do mês estourou? Então bloqueia e avisa.”

O painel nunca fala direto com serviços externos — só lê e escreve no Supabase.

[ Você ]
   │  cria pesquisa no navegador
   ▼
[ Painel Next.js ] ──grava──▶ [ Supabase / Postgres ]
   ▲                                      │  tarefas + cache + registro de consumo
   │ lê leads + scores                    ▼
   └───────────────────────── [ Worker (Node, sua máquina) ]
                                          │
                          ┌───────────────┴───────────────┐
                          ▼                               ▼
                 [ Cache ] → [ Orçamento ]            código próprio
                          │  (só passa se liberar)        (análise de site,
                          ▼                                score, sem custo)
        Google Places · PageSpeed · Meta Ad Library · IA (top N)
Duas recomendações que se mantêm Sem n8n no MVP — a orquestração é feita por funções TypeScript no worker (seção 07). E fontes plugáveis: existe uma “interface de fonte de dados” com dois métodos — descobrir(região, raio, nicho) e detalhar(placeId). Hoje só a implementação GooglePlaces existe; amanhã dá pra somar OSM, CNPJ ou entrada manual sem tocar em score, banco ou telas.

04 Estrutura das páginas

Poucas telas. O painel é operado, não lido.

/ — Painel

Lista das pesquisas já feitas, com data, nicho, quantidade de leads e status. Botão “Nova pesquisa”.

/pesquisa/nova — Formulário de pesquisa

Campo de região em texto simples (“Iguape SP”), controle de raio (ex.: 1–20 km), seleção de nicho, limite de leads (padrão 20) e filtros opcionais. Mostra a estimativa: “esta pesquisa deve usar ~1 chamada da Google”. Ao enviar, cria a pesquisa e enfileira a descoberta.

/pesquisa/[id] — Resultados

Tabela de leads ordenada por score. Mostra progresso do pipeline (“42 de 60 sites analisados”). Filtros, busca, ordenação, exportar CSV, marcar favorito.

/lead/[id] — Diagnóstico

A tela mais importante. Dados da empresa, “boletim” do site (cada teste como aprovado/reprovado), evidências de tráfego pago com nível de confiança, presença em redes, e o score aberto — quanto cada fator contribuiu. Embaixo, o resumo da IA (quando houver).

/config — Configurações e consumo

Chaves de API. Painel de consumo do mês: quantas chamadas Google Places / Geocoding / Details já foram feitas, com barra de progresso contra a cota gratuita e o teto que você definiu. Teto de gasto com IA. Validade do cache. Pesos do score (pra calibrar depois de ver leads reais).

Antes de qualquer Place Details, checa detalhes_em do mesmo jeito.

07 O papel do n8n

O que é, o que ele faria, e por que ele fica pra depois.

O n8n é uma ferramenta de automação visual: você monta fluxos arrastando “nós” (buscar dados → transformar → salvar no banco → chamar API) numa tela, sem escrever muito código. É ótimo pra conectar sistemas.

O que ele faria no Prospekta

Exatamente a orquestração do pipeline: receber a pesquisa do painel, disparar a descoberta, chamar cada etapa de enriquecimento, gravar no Supabase. É o mesmo trabalho do worker.

O ponto de decisão No MVP, n8n e worker resolvem o mesmo problema. Ter os dois é ter dois sistemas pra aprender, instalar (n8n exige Docker) e depurar. Para alguém começando e sozinho, isso mais que dobra a dificuldade sem entregar valor proporcional.

Recomendação prática

  • MVP: orquestração em TypeScript no worker. Você vê cada passo no código, depura num lugar só, e aprende os fundamentos.
  • Depois (quando o pipeline estiver estável e você quiser um painel visual pra ligar/desligar etapas, agendar reprocessamentos, ou plugar integrações prontas): sobe o n8n self-hosted via Docker e move a orquestração pra lá aos poucos. As funções de lib/ continuam as mesmas — o n8n só passa a ser quem as chama, via um endpoint HTTP no seu próprio app.

Ou seja: o projeto nasce pronto pra receber n8n, mas não paga o custo dele agora.

08 Google Places API: estratégia e cota gratuita

A resposta às 10 perguntas — como usar sem sair do R$ 0.

1 & 2 — Text Search, Nearby Search ou os dois?

Existem duas formas de descobrir empresas na Places API:

  • Text Search — você manda uma frase (“advocacia em Iguape SP”) e ela entende. Aceita qualquer nicho em texto livre, e resolve o nome da cidade sozinha.
  • Nearby Search — você manda um ponto + raio + um tipo da lista fixa da Google (“dentist”, “gym”, “restaurant”…). Não aceita texto livre, e muitos nichos brasileiros (“lanchonete”, “delivery”, “marmitaria”) não têm um tipo exato.
Recomendação Text Search como motor único do MVP. Funciona pra qualquer nicho, resolve a região sem chamada extra, e aceita o raio como restrição. Para “dentistas em Iguape SP” ela é claramente melhor: uma frase, uma chamada, 20 resultados. Nearby Search fica documentado como “segunda passada” futura — útil só quando o nicho casa com um tipo da Google e você quer pescar o que a Text Search deixou de fora.

3 — Como o raio entra

  1. Você digita a região em texto. O worker resolve pra coordenadas (1 chamada de Geocoding, guardada em cache — a mesma cidade nunca é resolvida duas vezes).
  2. Monta um círculo: centro + raio em metros (máximo da Google: 50.000 m).
  3. Passa esse círculo como locationRestriction na Text Search — resultado fora do círculo é excluído (não só “rebaixado”). Isso deixa o custo previsível: menos resultado irrelevante = menos enriquecimento à toa.

4 — Campos na primeira chamada (a mais importante)

Na Places API nova, você escolhe quais campos quer, e o preço da chamada sobe conforme os campos. A chave do custo mínimo é pedir só o necessário. Na descoberta, peça:

id                 ← o Place ID (essencial pra deduplicar)
displayName        ← nome
formattedAddress   ← endereço
location           ← latitude / longitude
types / primaryType← categoria
businessStatus     ← aberto? fechado definitivamente? (descarta lead morto cedo)
rating             ← nota
userRatingCount    ← nº de avaliações
websiteUri         ← site
nationalPhoneNumber← telefone

Parece muita coisa, mas é uma chamada só para os 20 leads, e já entrega tudo que o score baseado em regras precisa. Muito mais barato que economizar campos aqui e depois fazer 20 chamadas de Place Details.

5 — Campos que ficam para depois (Place Details, sob demanda)

Só quando você prioriza um lead ou abre a tela dele, 1 chamada de Place Details busca o que a busca não traz ou o que é caro:

  • reviews — os textos das avaliações (a faixa mais cara da API; no máximo 5)
  • regularOpeningHours — horário completo
  • internationalPhoneNumber, googleMapsUri e afins

Resultado guardado em places_cache.detalhes com data — nunca se chama Details duas vezes pro mesmo Place ID dentro da validade.

7 — Place ID contra duplicatas

O Place ID é o identificador único de um lugar na Google. Ele é a coluna google_place_id (única) em places_cache e leads. Fluxo: antes de gravar, upsert por Place ID — se já existe, atualiza “visto por último”, vincula à nova pesquisa em search_leads, e não cria lead duplicado nem faz chamada nova. Como reforço, uma deduplicação “fraca” por nome + endereço aproximado pega o caso raro do mesmo negócio com dois Place IDs (ou vindo de outra fonte no futuro).

9 — Como ficar dentro da cota gratuita

A Places API nova (modelo de 2025) dá uma cota mensal gratuita para cada tipo de chamada — na casa dos milhares de chamadas/mês por SKU. Confirme os números atuais no painel do Google Cloud, porque a Google mexe nisso. O plano pra nunca passar:

  • Uma pesquisa típica = 1 a 5 chamadas. Mesmo 100 pesquisas/mês × 5 = 500 chamadas, bem abaixo da cota.
  • Toda chamada é registrada em api_usage com custo estimado; o painel /config soma por mês e mostra a barra contra o limite.
  • Teto interno configurável (ex.: “parar de chamar Places depois de 3.000 no mês”) que o worker respeita antes de encostar no limite da Google.
  • Cache agressivo (Place ID + região).
  • Nada de Photos; nada de Autocomplete; Text Search em vez de Details-por-lead.

10 — Configurar quotas pra não tomar susto

  1. Projeto separado no Google Cloud só pro Prospekta — isola faturamento e limites.
  2. Billing → Orçamentos e alertas: orçamento de US$ 1 (ou 5) com e-mail em 50/90/100%. Alerta — não bloqueia.
  3. APIs e Serviços → [cada API] → Cotas: limite rígido de requisições por dia (ex.: Text Search 100/dia). Isso bloqueia de verdade — a chamada falha em vez de cobrar. É a rede de segurança real.
  4. Restringir a chave de API: só as APIs que você usa, e por IP. Chave vazada não vira conta alta.
  5. Teto no próprio app (o api_usage) como primeira barreira, antes mesmo da Google.
As outras fontes continuam Só a descoberta mudou. Continuam gratuitos e no plano: análise do site por código próprio, PageSpeed Insights (desempenho), Meta Ad Library (indícios de anúncio), RDAP (idade do domínio), e o site da própria empresa como fonte de redes sociais e contatos que faltarem.

09 Análises que NÃO precisam de IA

Tudo isso é código simples: baixar a página, procurar um padrão, marcar sim/não. IA aqui seria desperdício.

No site

  • Existe? — a URL responde
  • HTTPS — o endereço é https e o certificado é válido
  • Redireciona — pra onde vai a raiz do domínio
  • Mobile básico — tem a tag <meta viewport>? Usa media queries?
  • Desempenho — nota do PageSpeed; peso da página; tempo até o primeiro byte
  • WhatsApp — links wa.me / api.whatsapp.com
  • Telefone visível — links tel: ou número no texto
  • Formulário — existe uma tag <form>
  • CTA — botões com “orçamento”, “agende”, “fale conosco” (lista de termos)
  • Página de contato — link com “contato” / “fale”

Rastreamento e anúncios (no código da página)

  • Meta Pixel — connect.facebook.net, fbevents.js, fbq(
  • Google Analytics / GTM — googletagmanager.com, gtag(, IDs G- ou UA-
  • Google Ads — googleadservices.com, ID de conversão AW-
  • Remarketing/DoubleClick — doubleclick.net

Dados da empresa / redes

  • Nome, categoria, endereço, coordenadas, telefone, nota, nº de avaliações — vêm prontos da Google Places
  • Perfil de rede social existe (a URL abre)
  • Tem bio, tem link na bio
  • Data do último post e frequência (quando a página pública deixa ler)
  • Idade do domínio (RDAP)

Ferramentas que ajudam aqui: fetch (baixar), cheerio (procurar coisas no HTML), a API do PageSpeed. Nada disso é IA.

10 Análises que REALMENTE precisam de IA

Onde a resposta é interpretação, julgamento ou texto — não um sim/não.

  • Diagnóstico comercial do lead — ler todos os sinais e dizer, em linguagem de vendedor: “empresa movimentada, mas o site não converte: sem WhatsApp, sem formulário, lento no celular. Ângulo de entrada: oferecer uma landing page de captação.”
  • Qualidade das peças de rede social — só um modelo com visão, olhando prints dos posts, consegue opinar sobre identidade visual, consistência e capricho.
  • Clareza da bio e do CTA — “a bio diz o que a empresa faz e como agir?” é julgamento de linguagem.
  • Resumo executivo — juntar site + anúncios + redes + score numa recomendação curta e priorizada.
  • Abordagem personalizada (fase futura) — escrever a primeira mensagem.
  • Classificar categoria ambígua (opcional) — quando a tag do OSM é vaga (“loja”) e o nome sugere o nicho.
Regra de ouro do custo A IA só roda depois do score, e só nos leads do topo (ex.: os 20% melhores, ou os que passaram de 60 pontos). Modelo barato (Gemini Flash, GPT-4o-mini ou Claude Haiku). Com esse recorte, analisar uma pesquisa inteira custa centavos de dólar. Guarde o custo de cada chamada na tabela ai_diagnoses pra acompanhar.

11 Como construir o Score de Oportunidade

Um número de 0 a 100 que responde “quanto vale a pena eu abordar esta empresa?” — não “quão bom é o marketing dela?”.

A ideia central que você trouxe está certa: oportunidade = tem negócio de verdade × tem problema que eu resolvo × dá pra falar com ela. Uma empresa movimentada com site ruim vale mais que uma empresa fantasma com Instagram bonito.

Cinco fatores, com pesos

Negócio ativo / capacidadepeso 25
Tem telefone, endereço, horário, algum site. Sinais de que é um negócio vivo. Pontuação baixa aqui derruba o lead — não adianta ter problema se não tem quem resolver.
Atividade / reputaçãopeso 20
Volume de avaliações (em escala logarítmica) e nota média — agora disponíveis pela Google Places. Mostra que tem clientes e se importa.
Problemas que você resolvepeso 35
O coração do score. Ponto para cada falha vendável: sem site, sem HTTPS, não é mobile, lento, sem WhatsApp, sem formulário/CTA, sem Pixel (não remarketa), sem Analytics (está no escuro), rede social fraca, sem indício de tráfego pago. Cada item = uma oferta sua.
Facilidade de contatopeso 10
WhatsApp ou telefone direto disponível; negócio pequeno (o dono atende). Lead ótimo que você não consegue contatar não é lead.
Sinais de que investepeso 10
Já gasta com algo: tem site pago, já rodou anúncio, usa ferramenta paga. Quem já investe, volta a investir.

Regras que evitam distorção

  • “Problemas” só contam se “Negócio ativo” for razoável. Site inexistente numa empresa fantasma não é oportunidade — é lixo. Multiplique o fator 3 por um coeficiente do fator 1.
  • Teto por fator. Um único problema catastrófico não leva o score a 100; a soma de vários problemas médios, sim.
  • “Sem marketing nenhum” é ambíguo. Pode ser ouro (ninguém explorou) ou deserto (sem verba, sem interesse). Os fatores 1 e 5 desempatam.
  • Score determinístico. É uma fórmula em código, testável e explicável. Nada de IA no número. A IA só escreve o texto ao lado.
  • Transparência total. Guarde a contribuição de cada fator e mostre na tela do lead: “68 = 18 (ativo) + 8 (reputação) + 30 (problemas) + 8 (contato) + 4 (investe)”.
  • Versão da fórmula. Salve versao_formula em cada score. Quando ajustar os pesos, você sabe o que foi calculado com qual regra.

Como calibrar: rode numa cidade/nicho que você conhece, olhe os 20 primeiros e os 20 últimos. Se algum lead “obviamente bom” ficou embaixo, ajuste o peso e rode de novo. É iterativo.

15 Limitações das fontes

O que a Google Places e as fontes gratuitas não resolvem — pra ajustar a expectativa desde já.

  • Places só conhece quem está no Google Maps. Uma empresa que nunca criou ficha no Maps não aparece — e essa é justamente parte do público de baixa presença digital. Você vê os que têm alguma presença.
  • A cota gratuita pode mudar. A Google reestruturou o modelo em 2025 e pode mexer de novo. Confirme os limites atuais e mantenha as cotas rígidas configuradas.
  • Custo cresce com os campos. Pedir reviews em massa sai caro. Por isso os textos de avaliação só vêm sob demanda, no lead priorizado.
  • Sem CNPJ nem dados de faturamento. Places não diz porte da empresa nem situação cadastral — isso viria dos dados abertos da Receita, numa fase futura.
  • Mercado pequeno. Na sua região, cada nicho tem poucas dezenas de empresas. É limitação do lugar, não da API.
  • PageSpeed API: tem cota diária, às vezes demora, e só emula mobile.
  • Meta Ad Library API: acesso completo é restrito; em vários países entrega só anúncios políticos. O site mostra tudo, mas ler de forma automática é frágil.
  • Google Ads Transparency: sem API. Só manual ou raspagem instável.
  • Redes sociais: contagem de seguidores, frequência de posts e prints das peças dependem de páginas públicas que mudam e bloqueiam. Trate como bônus, não como base.
  • IA local (Ollama): grátis, mas exige um PC razoável e entrega qualidade inferior às APIs pagas para diagnóstico comercial.

→ Posição final

O resumo do que eu faria no seu lugar.

  1. Google Places como fonte única do MVP, via Text Search, atrás de uma interface de fonte plugável. OSM e CNPJ entram depois sem reescrever nada.
  2. Custo controlado por construção, não por disciplina. Cota rígida diária no Google Cloud (bloqueia, não cobra) + teto interno no api_usage + orçamento por pesquisa + cache por Place ID. Os módulos budget/cache/usage vêm antes da descoberta no cronograma.

A Anexo — Configurar o Google Cloud com trava de custo

Uma vez só, ~30 minutos. No fim você tem uma chave de API que, mesmo com um bug no código, não vira conta alta.

Antes de começar — entenda uma coisa A Places API exige um cartão de crédito cadastrado, mesmo pra usar só a cota gratuita. Isso é normal e inevitável. O cartão só é cobrado se você passar da cota grátis e não tiver colocado os limites deste anexo. Vamos colocar os limites justamente pra isso não acontecer.
  1. Criar o projeto
    Entre em console.cloud.google.com com sua conta Google. Na barra de cima, no seletor de projeto, clique em Novo projeto. Nome: prospekta. Sem organização. Criar e selecionar esse projeto.
  2. Ativar o faturamento (billing)
    Menu ☰ → Faturamento. “Vincular uma conta de faturamento” → adicionar cartão. Sem isso as APIs não funcionam. Deixe anotado onde fica o botão “Desativar faturamento” (Faturamento → Gerenciamento da conta) — é o seu freio de emergência absoluto.
  3. Ativar as 3 APIs
    ☰ → APIs e serviços → Biblioteca. Procure e clique em Ativar em cada uma:
    · Places API (New) — a “nova”, não a antiga “Places API”
    · Geocoding API
    · PageSpeed Insights API
  4. Criar a chave de API
    APIs e serviços → Credenciais → Criar credenciais → Chave de API. Copie a chave. Ela vai no arquivo .env.local do projeto (que o Next.js já ignora no Git) como GOOGLE_MAPS_API_KEY=.... Nunca coloque essa chave em código que roda no navegador — só o worker (servidor) usa.
  5. Restringir a chave reduz o estrago se ela vazar
    Clique na chave recém-criada:
    · Restrições de API → “Restringir chave” → marque só Places API (New), Geocoding API e PageSpeed Insights API.
    · Restrições de aplicativo → como o worker roda na sua casa (IP que muda), durante o desenvolvimento pode deixar Nenhuma; se um dia rodar num servidor fixo, mude pra Endereços IP e ponha o IP dele.
  6. Cotas rígidas — a rede de segurança de verdade isto bloqueia, não só avisa
    Para Places API (New) e depois Geocoding API: abra a API → aba Cotas e limites do sistema. Procure o limite de requisições por dia (ou por minuto, se não houver o diário). Clique no lápis e reduza pra um número baixo — ex.: Places 200/dia, Geocoding 100/dia. Acima disso, a chamada falha com erro em vez de gerar cobrança. Você aumenta depois se precisar.
    Observação: em algumas SKUs da Places nova só existe limite por minuto, não por dia. Onde não houver o diário, o teto interno do app (o api_usage, seção 08) + o alerta de orçamento abaixo cobrem essa folga.
  7. Alerta de orçamento avisa, não bloqueia
    Faturamento → Orçamentos e alertas → Criar orçamento. Escopo: só o projeto prospekta. Valor: US$ 1. Alertas por e-mail em 50%, 90% e 100%. Se você receber esse e-mail, algo está errado — investigue na hora.
  8. Testar 1 chamada
    No terminal do VS Code, rode o teste abaixo (troque SUA_CHAVE). Se voltar uma lista de escritórios de Iguape, está tudo certo. No dia seguinte, confira em Faturamento → Relatórios que ficou em US$ 0 (dentro da cota grátis).

Repare no cabeçalho X-Goog-FieldMask: é ele que controla o custo. Só os campos listados ali são retornados e cobrados. Pedir places.id e nomes é a faixa mais barata; adicionar places.rating, places.websiteUri, places.nationalPhoneNumber sobe de faixa — mas ainda assim é uma chamada pros 20 resultados.

Resultado Ao terminar este anexo você tem: um projeto isolado, 3 APIs ativas, uma chave restrita, um limite diário que trava o consumo, e um alerta em US$ 1. A partir daqui, o pior caso de um bug no código é “as chamadas pararam de funcionar” — nunca “chegou uma fatura”.
